# Button Box — context and handoff

## Goal
USB button box for SimHub: HID Game Controller with 32 buttons + encoders,
recognized in Windows' `joy.cpl`.

---

## Part 1 — STM32F103 (abandoned). What was investigated

Project: `~/Projects/arduino/STM32-SimHub-ButtonBox` (PlatformIO + TinyUSB + stm32cube).
Composite USB: HID gamepad (32 buttons, Report ID 1) + CDC ACM.

**Symptom:** the device enumerates and shows up in `joy.cpl` with 32
buttons, status OK, but NO button triggers — not even a heartbeat
generated by the firmware itself that toggles button 31 every 1s. The CDC
worked fine (PING/PONG responding).

### Measurements taken via SWD (ST-Link + OpenOCD, with the CPU running)

- The firmware **reads the pin and builds the correct report**:
  `s_report_work` with bit0=1 when closing the GND→PB9 jumper.
- `send_count` **increments** (reports accepted and transmitted by the USB
  stack).
- HID IN endpoint (TinyUSB mapped it to `EP1R` with `EA=3`):
  **`STAT_TX=VALID` stuck** — the report stays loaded in the buffer and
  the host **stops sending IN tokens**.
- Clock **exactly 48 MHz**: `RCC_CR` with HSERDY+PLLRDY, `RCC_CFGR` with
  PLL×9 and USBPRE=/1.5.
- USB IRQ enabled in the NVIC, no stuck interrupt, active bus (SOF), no
  suspend.
- Report descriptor read from the binary — textbook, no error:
  `05 01 09 05 A1 01 85 01 05 09 19 01 29 20 15 00 25 01 75 01 95 20 81 02 C0`
- R10 (D+ pull-up) measured by the user: **1.5 kΩ** (correct).
- **The number of reports delivered before it locks up is RANDOM**: 7, 8,
  14, 23, 68, 90, 337. Not a deterministic limit — it's an intermittent
  failure.

### Attempts that did NOT fix it

1. Disconnect pulse on D+ (PA12 low for 50 ms) at boot. *Fixed a
   different, real problem* — without it, after flashing via SWD the host
   doesn't re-enumerate and the device stays in a stale state (`cfg=0`
   stuck) until a physical replug. Verified: with the pulse, `cfg` goes
   to 1 on its own. But it didn't fix the buttons.
2. Implementing `tud_hid_get_report_cb` (it was a stub returning 0).
3. Removing the Report ID from the descriptor and sending without a
   prefix.
4. Adding a dummy X/Y axis — `joy.cpl` started showing "2 axes and 32
   buttons", but buttons still didn't trigger.
5. Changing the PID several times (0007→000A) to defeat Windows'
   descriptor cache.
6. Lowering the polling rate: `bInterval` 8→32 ms gave the identical
   failure; 64 ms made Windows **de-configure** the device (`cfg=0`).
7. **HID-only** build (no CDC, no IAD, 1 interface): **identical
   failure** — so composing with CDC isn't the variable.

### Likely cause: the MCU is a clone

Read via SWD:
- `DBGMCU_IDCODE = 0x20030410`
- Flash-size register = **128 KB** on a chip sold as a C8 (64 KB)
- **96-bit UID at `0x1FFFF7E8` = ALL ZERO**

A genuine ST STM32F103 always has a unique factory UID. A zeroed UID
means CKS32/CS32/APM32. The observed pattern (CDC **bulk** endpoints
work, HID **interrupt IN** endpoint never sustains) is consistent with a
USB quirk in these clones.

### STM32 project status
**Reverted to the original** at the user's request, and the original
composite firmware was reflashed onto the board. No experimental change
was left in place.

## Part 2 — Decision to switch boards

Hard constraint raised before investing more time:
- **ESP32-C3 / C6** (the best-selling "Super Mini"): native USB is a
  fixed-function *USB Serial/JTAG* → CDC only. **No HID.** Dead end.
- **ESP32-S2 / S3**: full USB OTG → TinyUSB → **HID works**.

Confirmed via esptool that the user's board is an **ESP32-S3 (QFN56) rev
v0.2, 4 MB XMC flash, 2 MB quad PSRAM, 40 MHz crystal**.

Deciding factor: the user **already had working HID gamepad code** in
`~/Projects/arduino/ESP-SimHub-ESP32S3-SCREEN/src/main_buttons.cpp`
(`USBHIDGamepad`, 32 buttons + 4 axes).

### Result
Test project: `~/Projects/arduino/esp32s3-buttonbox-test`

**HID WORKS.** macOS attached the driver (`PrimaryUsage=5` = Gamepad) and
`InputReportCount` keeps climbing (126→134→143). On Windows, Button 32
blinks in `joy.cpl`. A direct contrast with the STM32.

## ESP32-S3 gotchas discovered (important)

1. **`ARDUINO_USB_MODE=0` is mandatory for HID** (USB-OTG/TinyUSB). With
   `=1` the core uses the hardware USB-Serial-JTAG, which **doesn't do
   HID**. The board JSON forces `=1`, so it has to be overridden via
   `board_build.extra_flags` — `build_flags` alone doesn't win.
   > **Finding for the ESP-SimHub project:** the `dingyimei-s3-zero` env
   > has `ARDUINO_USB_MODE=1` while `main_buttons.cpp` uses
   > `USBHIDGamepad`. **HID doesn't work in that mode.**
2. **Board definition matters:** using `esp32-s3-devkitc-1` (8 MB, no
   PSRAM) on a 4 MB chip caused a **BOOT LOOP**. The correct one is the
   custom `esp32-s3-fh4r2` board (4 MB + 2 MB quad PSRAM,
   `partitions=default.csv`), which already exists in
   `ESP-SimHub-ESP32S3-SCREEN/boards/`.
3. After an esptool reset the board stays in **DOWNLOAD mode**
   (`boot:0x20`); only a **physical power cycle** boots the app.
4. With `MODE=0` the USB-Serial-JTAG disappears, so esptool **can't
   auto-reset** via the TinyUSB CDC → flashing over cable requires
   holding BOOT. `upload_speed=115200` **doesn't fix it** (tested).
5. **WiFiManager:** `autoConnect()` reopens the portal on every failure
   and the board gets stuck in AP mode forever. Better: connect with a
   saved/fixed credential and keep retrying on its own; only open the
   portal on explicit request.
6. **`WiFi.setSleep(false)` only AFTER `WiFi.begin()`.** Called before
   the mode is chosen, it initializes the radio in STA and prevents the
   AP from coming up.
7. **Don't write to Serial during OTA** — writing to the TinyUSB CDC
   blocks when the host isn't reading, stalling the loop.
8. **`espota` doesn't resolve mDNS `.local`** — it needs the IP.

## ESP32-S3 project status at the time

Working (verified):
- HID gamepad (Button 32 heartbeat, Button 1 = board's BOOT button)
- WiFi connecting on its own (`Orlando_tplink`, `192.168.0.117`, RSSI −64)

Failing (verified):
- **OTA**: transfers 100% and breaks on verification with
  **`Flash Read Failed`**
- **USB flashing without the BOOT button**

Fixes prepared but **NOT tested** (the board had been disconnected):
- `-DBOARD_HAS_PSRAM` — hypothesis for the `Flash Read Failed`: the board
  uses `memory_type=qio_qspi` (flash + PSRAM); without declaring the
  PSRAM, re-reading flash during OTA verification fails. The equivalent
  env in ESP-SimHub, which works, has the flag.
- `enter_bootloader.py` script without DTR/RTS toggling (opening the port
  reset the board before it could read the `BOOTLOADER` command, which
  forces download mode in software via `RTC_CNTL_FORCE_DOWNLOAD_BOOT`).
